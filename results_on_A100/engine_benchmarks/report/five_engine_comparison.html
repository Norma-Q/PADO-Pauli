1문제 정의 — 세 갈래 비교

파울리 전파 구현 다섯 개를 한 줄로 세우는 것은 의미가 없음. 하드웨어도 다르고, 절단 파라미터의 의미도 다르고, 기울기를 내는 엔진과 못 내는 엔진이 섞여 있음. 대신 통제 변수가 다른 세 개의 비교로 나눠 읽음.

비교 1 · cuPauliProp vs PADO
통제: 같은 GPU, 같은 max_weight 의미론, 양쪽 다 기울기 지원 — 남는 변수가 구현뿐이라 가장 깨끗한 like-for-like임. (§4)
비교 2 · Julia surrogate vs PADO
통제: 같은 설계 철학 — 파라미터 없이 회로 구조만 컴파일하고, ⟨0|·|0⟩에 기여하지 않는 항을 걸러낸 뒤 반복 평가. 수학이 같음을 항 수가 증명함. 남는 변수는 산출물의 자료구조와 하드웨어. (§5)
비교 3 · 5엔진 전체 지형
통제 없음. "이 박스에서 이 문제 크기라면 무엇을 쓸까"에 답하는 실용 비교. (§6)

Qiskit pauli-prop은 비교 1·2 어디에도 들어가지 않음 — 가중치 상한 개념이 없어 max_terms로 대신하고(§7.2), 기울기 API가 없어 통제 조건을 공유하지 못함. 비교 3에서 지형의 일부로만 다루고, 그 위치는 §6.6에서 따로 정리함.

2실험 설계

회로는 오케스트레이터가 한 번 생성한 게이트 리스트로 미리 만들어 다섯 워커에 그대로 전달하고, 워커마다 별도 서브프로세스로 격리함. 케이스당 5회 반복(rep 0–4), rep 0은 warmup, steady = rep 1–4 평균. 기준값은 PennyLane float64 상태벡터(기댓값 + 중앙차분 h=10⁻⁴ 기울기 4성분). CPU 엔진 timeout 900 s. 4개 묶음 · 16개 케이스 · 5엔진 = 80런, 69 Success / 7 Timeout / 1 Skipped / 3 Unsupported.

4비교 1 — GPU 대결: cuPauliProp vs PADO

같은 A100, 같은 max_weight 의미론, 양쪽 다 기울기 API 보유. 하드웨어·절단·기능이 모두 고정이라 남는 변수가 구현뿐임 — 이 문서에서 가장 조건이 깨끗한 비교임.

4.1 시간 — 격차가 항 수와 함께 단조 증가

가장 작은 케이스에서 이미 PADO가 앞서고(255항에서 순전파 2.7배, 역전파 2.2배), 항 수가 커질수록 벌어져 1,678만 항에서 순전파 10.1배·역전파 15.4배가 됨. 역전파 쪽 기울기가 더 가파른 것이 일관된 패턴임 (mw=6에서도 10.1배 대 15.0배). 원인은 §6.1의 스케일링에 있음 — cuPauliProp은 전파 항 전체를 매 평가마다 다시 만들고, PADO는 컴파일 때 걸러 둔 수천 개만 반복 평가함.

4.2 메모리 — 작은 케이스는 동률, 큰 케이스에서 갈림

점유 비는 작은 케이스에서 0.97–1.01배로 사실상 동률임. 두 엔진 다 CUDA 컨텍스트·라이브러리 바닥 ~1.4 GB에 앉아 있어 자료구조 차이가 드러나지 않기 때문임. 항 수가 커지면 갈라져 mw=4 1.45배 → mw=5 2.56배 → mw=6 3.14배 (46,494 MB 대 14,810 MB). 원자료와 GPU 전용 분석은 표 4·그림 6과 GPU 페어 문서에 있음.

4.3 기울기 — 한쪽만 항 수와 함께 열화

둘 다 float32라 분해능 바닥이 ~10⁻⁷로 같음. PADO는 무절단 전 구간에서 그 바닥에 머물지만 (5.5×10⁻⁸ ~ 1.1×10⁻⁷), cuPauliProp은 26만 항부터 바닥을 벗어나 7.7×10⁻⁵ → 1.3×10⁻³ → 1,678만 항에서 1.8×10⁻²가 됨. 기댓값은 두 엔진 모두 10⁻⁷대로 멀쩡하므로 역방향 누적의 수치 문제로 보이나, 이 데이터로 원인을 특정할 수는 없음(그림 7, 표 5).

4.4 배치는 이 비교 밖의 이야기

임베딩 배치에서 시간 비는 21배(bs=10) → 206배(bs=300)까지 가지만, 이는 native 배치 축이 PADO에만 있어서지 커널 효율의 차이가 아님(§7.3). 같은 구간에서 점유 비는 역전됨 — bs=300에서 0.21배로, PADO가 배치 전체의 버퍼를 들고 있기 때문임. 배치 속도를 메모리로 지불하는 구간임.

5비교 2 — 컴파일-재사용 대결: Julia surrogate vs PADO

둘 다 파라미터 값 없이 회로 구조만 먼저 전파해 재사용 가능한 산출물을 만들고, ⟨0|·|0⟩에 기여하지 않는 항을 걸러낸 뒤 파라미터를 넣어 반복 평가함. 설계 철학이 고정이므로 남는 변수는 산출물의 자료구조와 하드웨어임.

5.1 같은 설계임을 항 수가 증명함

제로 필터의 기준이 문자 그대로 같음 — PP.jl은 containsXorY로 X·Y를 포함한 파울리 문자열을 버리고, PADO는 x_mask == 0인 행(Z-only)만 남김. 우연이 아님은 항 수가 보여줌: 두 엔진이 모두 완주한 10개 케이스 전부에서 전파 항 수와 평가 항 수가 완전히 일치함. 같은 근사를 같은 크기로 압축한다는 뜻임.

5.2 갈리는 곳 셋

  • 산출물의 그릇. surrogate는 포인터로 연결된 가변 노드 DAG임 (PauliRotationNode가 부모 목록·trig_inds·signs·param_idx를 들고, 평가는 최종 경로에서 시작하는 재귀 순회 + 메모이제이션). PADO는 평탄한 텐서와 스텝별 희소 행렬이고 (v_out = M_const·v + cosθ·M_cos·v + sinθ·M_sin·v), 평가는 그 연쇄의 곱임. 같은 수학을 담는 그릇이 포인터 그래프냐 배치 가능한 선형대수냐의 차이이고, §5.3 성능 격차의 대부분이 여기서 나옴.
  • 필터가 닿는 범위. PP.jl의 zerofilter!는 최종 PauliSum을 잘라냄 (도달 불가능해진 부분 그래프는 참조가 끊겨 사라짐). PADO는 keep mask를 스텝 연쇄를 따라 역방향으로 전파한 뒤 입력 basis까지 줄임. 최종 평가 항 수는 같지만 PADO 쪽은 중간 표현도 함께 줄어듦.
  • 미분 가능성이 설계에 들어 있는지. PADO의 산출물은 미분 가능한 프로그램이라 diff_mode="vjp"로 기울기가 나옴. surrogate의 노드는 cummulative_value::Float64로 고정돼 있고, 업스트림 주석이 "자동미분 라이브러리를 쓰려면 이걸 Real로 바꿔야 한다"고 적어 둠 — 기울기는 빠뜨린 기능이 아니라 아직 열지 않은 설계임. 계수 절단이 불가능한 것도 같은 이유로, 전파 중 계수가 숫자가 아니라 노드이기 때문임.

5.3 성능은 문제 크기가 가름

작은 케이스에서는 surrogate가 더 빠름 — mw=2(426항)에서 0.0025 s 대 PADO 0.0267 s로 10.6배, 2x2(255항)에서 0.0012 대 0.0050 s로 4.3배. §6.2와 같은 이유로 GPU 상수 비용이 지배하는 구간임. 교차는 항 수 426 ~ 4,095 사이에서 일어나고, 그 뒤로는 벌어짐 — 3x3 253배, mw=5 321배, 2x5 470배. 이 배수는 배치를 쓰지 않은 단일 샘플 1 step끼리의 비임 — 여덟 케이스 모두 배치 크기가 1이고 PADO의 native 배치도 꺼져 있으므로, 배치가 부풀린 수치가 아님. 대신 GPU 대 CPU라는 유보가 붙음(§7.1). 구축 비용은 전 구간 PADO가 유리하며(2.5 ~ 123배), mw=6·3x4에서는 구축 자체가 timeout임. 표 3에 5엔진 셋업 시간이 있음.

5.4 메모리 — 바닥은 surrogate가 낮고, 자라는 속도는 PADO가 완만함

재사용형 설계의 값은 상주 산출물이 얼마나 무거운가이므로, 두 엔진의 점유는 이 비교에서 시간만큼 중요함. 다만 PADO는 VRAM, surrogate는 RSS라 종류가 다른 메모리이므로 비를 만들지 않고 절대량을 나란히 둠(§7.1). 자라는 양은 둘 다 "상주 산출물이 항 수를 따라 얼마나 커지는가"라 견줄 수 있음.

바닥은 surrogate가 낮음 — 가장 작은 케이스에서 638 MB로, PADO의 1,423 MB(대부분 CUDA 컨텍스트) 절반 이하임. 그런데 항 수를 따라 자라는 양이 정반대임: 가중치 절단 스윕 mw=2 → mw=5 구간에서 PADO는 +2,040 MB(1,425 → 3,466), surrogate는 +9,908 MB(638 → 10,546)로 4.9배 가파름. 두 곡선은 mw=4(134,001항)에서 1,644 대 1,651 MB로 거의 정확히 만나고, 그 위로는 격차가 벌어져 mw=5에서 3.0배, 2x5에서 2.9배가 됨. 평가 항 수가 같은데도(§5.1) 상주량이 이렇게 갈리는 것은 §5.2의 첫 항목 — 포인터로 연결된 노드 하나하나가 부모 목록·삼각함수 인덱스·부호 배열을 들고 있는 그래프와, 같은 정보를 평탄한 배열과 희소 행렬에 담은 표현의 차이임. mw=6에서 surrogate의 구축이 timeout으로 끝난 것도 이 성장의 연장선에 있음.

5.5 시간이 뒤집히는 지점과 메모리가 뒤집히는 지점은 다름

그림 3과 그림 4는 가로축이 같으므로 좌우 위치를 견줄 수 있는데, 그러면 두 교차가 두 자릿수 넘게 떨어져 있음이 드러남 — 시간은 항 수 426 ~ 4,095에서 뒤집히고, 메모리는 134,001에 가서야 같아짐. 세로축의 종류가 달라서(배수 대 MB) 생기는 착시가 아니라, 시간과 메모리가 서로 다른 속도로 갈리기 때문임.

6비교 3 — 5엔진 전체 지형

통제 변수 없음. "이 A100 박스에서, 이 문제 크기라면 무엇을 쓸까"에 답하는 실용 비교임. 따라서 여기의 배수는 구현 품질의 비가 아니라 선택의 근거로만 읽어야 함(§7.1).

6.2 문제 크기가 최속 엔진을 바꿈

표 1의 굵은 값(행별 최속)을 항 수 순으로 늘어놓으면 경계가 뚜렷함:

6.6 Qiskit의 위치 — 왜 비교 1·2에 없는가

Qiskit pauli-prop은 두 통제 조건을 다 벗어남. 가중치 상한 개념이 없어 max_weight 스윕을 max_terms로 대신하므로 mw 묶음의 Qiskit 점들은 같은 절단이 아니고, 기울기 API가 없어 비교 1의 기울기 비교에도 들어갈 수 없음. 컴파일-재사용 설계도 아니라 비교 2와도 무관함.

그럼에도 전체 지형에서 두 가지를 보여줌. 첫째, 메모리 기준선 — 100–540 MB는 5엔진 중 압도적으로 작고, "파울리 전파 자체가 메모리를 많이 먹는 계산은 아니다"라는 사실을 상기시킴(무거운 것은 항 수를 다 들고 있는 전략임). 둘째, CPU 참조점 — Rust 가속 구현이 순수 Julia 대비 어디쯤인지를 보여줌. 실제로는 대부분의 케이스에서 Julia보다 느리고 (mw=6에서 123.8 s 대 25.9 s), 가장 작은 케이스 몇 개에서만 앞섬. 기댓값 정확도만큼은 5엔진 중 최고 수준임(무절단에서 10⁻¹⁵~10⁻¹³).

7비교가 성립하지 않는 구간

7.1 GPU 대 CPU (비교 3 전반)

하드웨어가 다름. GPU 엔진의 시간에는 A100의 병렬성이, CPU 엔진의 시간에는 이 박스 CPU의 성능이 들어 있음. 따라서 비교 3의 GPU/CPU 간 배수는 "이 박스에서의 실용 선택" 근거이지 구현 품질의 비가 아님. 메모리도 마찬가지 — VRAM 점유와 RSS 점유는 종류가 달라 비율을 만들지 않았고, GPU 쪽 ~1.4 GB는 CUDA 컨텍스트 바닥이라 CPU 쪽 수치와 나란히 읽으면 안 됨. 비교 1은 이 문제가 없음(양쪽 다 같은 A100). 비교 2는 GPU 대 CPU이므로 §5.3의 배수에는 이 유보가 붙음 — 다만 항 수 일치(§5.1)와 구축·평가의 설계 차이(§5.2)는 하드웨어와 무관한 사실임.

7.2 절단 의미론이 세 갈래임

같은 숫자를 넣어도 다른 근사가 나옴. 가중치 상한: cuPP·PADO·Julia·surrogate는 같은 max_weight를 공유하지만 Qiskit은 개념이 없어 max_terms로 대신함 — mw 스윕의 Qiskit 점들은 같은 절단이 아님. 계수 컷오프: cuPP·Julia는 전파 중 매 게이트, PADO는 컴파일 시 한 번(build_min_abs), Qiskit은 atol, surrogate는 불가. coeff_truncation 묶음의 엔진 간 정확도 차이는 품질이 아니라 의미론 차이이므로 인용하지 않는 것이 맞음.

7.3 배치 격차는 API 설계를 반영함

native 배치 축이 PADO에만 있음. 나머지 넷은 샘플 단위 루프를 돌 수밖에 없어 처리량이 배치와 무관하게 고정됨. 배치 구간의 배수(비교 1의 206배, 비교 3의 표 7)는 커널·코어 효율 비교가 아니라 배치 축의 유무를 반영함. 다만 파라미터 스윕·학습 루프처럼 한 회로에 여러 파라미터를 흘리는 실사용에서는 그 설계 차이가 곧 성능 차이가 됨.

7.4 기타 유보

  • timeout(900 s)은 상한이지 실측이 아님. 3x4의 CPU 엔진들이 "900 s 걸린다"가 아니라 "그 안에 못 끝낸다"임.
  • Julia의 tfwdbwd는 결합 시간임. 타 엔진 tbwd와 직접 비교 불가, tfwd+tbwd와 대응.
  • surrogate는 업스트림 legacy 코드임. PP.jl이 제거 예정으로 표시한 실험 모듈이므로, 비교 2의 결과를 PauliPropagation.jl 전체의 평가로 읽으면 안 됨(§2.1).
  • 단일 런임. steady는 rep 1–4 평균이고 런 간 재현성은 repeat_timing 실험 소관. 이 런의 fwd RSD 중앙값 0.84%, 단발 스파이크 1건(PADO bs=100 rep 2).
  • CPU 엔진의 스레드 활용은 측정하지 않았음. 각 SDK의 기본 설정 그대로 실행함.

8결론

비교 1 — GPU 대결

  1. 조건이 가장 깨끗한 비교에서 PADO가 전 구간·전 지표 우세이고, 격차가 항 수와 함께 단조 증가함 — 순전파 2.7배(255항) → 10.1배(1,678만 항), 역전파 2.2 → 15.4배.
  2. VRAM 점유는 작은 케이스에서 동률(둘 다 ~1.4 GB 컨텍스트 바닥), 큰 케이스에서 3.1배(mw=6).
  3. 기울기는 PADO만 바닥(~10⁻⁷)을 유지하고 cuPauliProp은 26만 항부터 열화해 1.8×10⁻²까지 감.

비교 2 — 컴파일-재사용 대결

  1. 같은 설계임이 확인됨 — 제로 필터 기준이 문자 그대로 같고, 양쪽 완주 10케이스에서 전파·평가 항 수가 완전히 일치함.
  2. 갈리는 곳은 산출물의 그릇(포인터 DAG 대 희소 행렬 연쇄), 필터가 닿는 범위, 미분 가능성, 그리고 문제 크기 — 작은 케이스는 surrogate가 빠르고(mw=2에서 10.6배) 교차(426~4,095항) 후 PADO가 수백 배 앞섬. 구축은 전 구간 PADO 우세.

비교 3 — 전체 지형

  1. 문제 크기가 최속 엔진을 바꿈 — 항 ≲2,000이면 Julia/surrogate, ≳4,000이면 PADO, ≳10⁷이면 GPU만 완주.
  2. 메모리 최검소는 Qiskit(≤540 MB), 최대는 surrogate(상주 그래프 10.5 GB). 절대 점유 계측이 처음 드러낸 사실임.
  3. 기울기를 낼 수 있는 엔진은 셋뿐이고 바닥이 자료형별로 다름 — 속도와 기울기 정밀 바닥을 함께 갖는 것은 PADO뿐임.
  4. native 배치는 PADO 독점(bs=300에서 5,658 eval/s 대 ≤28). 단 이는 배치 축의 유무를 반영함.

A부록 — rep별 원시 측정값

Success 레코드만 수록. 회색 배경의 rep 0은 warmup — 시간의 steady 평균에서 제외되고, 점유 평균에는 포함됨.
